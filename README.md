# HiFAST-X-Purge-the-mistake

**hifast 的质量检查、过程可观测与可交接层**

 **Purge the Mistake**——让错误在造成损失之前被发现：写错在启动前拦住，
跑偏在处理中看见，坏结果在下游之前挡下

[HiFAST](https://hifast.readthedocs.io) 是 FAST 中性氢（HI）数据处理链，
科学算法经过大量实测检验。但缺少对其进行质量检测的方法

> **不 fork、不改源码、不改算法、不改默认参数、不改 HDF5 数据结构。**
> 卸载后 `python -m hifast.*` 行为完全恢复。

**当前状态：规格阶段，代码尚未开始。** 本仓库目前只有 [规格说明书](docs/00_软件工程目标与范围.md)。

| 对象软件 | hifast v1.3a3（GitHub `be6d5f8`，2024-07-03），27 个顶层模块，约 1.87 万行 Python |

## 为什么需要这一层

| 现象 | 后果 |
|---|---|
| 参数只做语法/类型校验，不做语义校验，`--help` 只写变量名不写物理含义 | 区间反序、混淆噪声窗口与信号窗口、少给一个值这类错误，往往在跑了几十分钟、吃掉大量内存后才暴露；更糟的是不报错但结果错 |
| 同一科学目标有多种等价参数组合，代价不写在文档里 | 调参靠口口相传与反复试错，经验无法沉淀 |
| 只有各阶段内部的局部 tqdm | 看不到"第几束 / 共几束、整批还剩多久、当前占多少内存"；长任务必须人守着 |
| 每个阶段结束没有任何自动检查 | 坏数据、误标掩膜、阶段不一致只能靠事后人工比对发现，发现越晚重跑越贵 |
| RFI 掩膜要先去别的软件画区域、存成 `.reg` 再回终端应用 | 标注过程跨两个软件、无法版本化，区域文件的语义陷阱容易造成数据损失 |
| 没有 manifest，靠文件名后缀和目录判断进度 | 目录里混进不同阶段文件、半成品被当成成品跳过 |
| 经验散落在长篇状态文档与脚本注释里 | 换人接手要通读数千行，参数为什么这么选没人说得清 |

共同点：**代价在事后才显现**。所以改进的核心不是"多几个功能"，
而是把判断从"跑完再人工看"提前到"启动前 + 处理中 + 处理完自动出结论"。

## 改进是怎么做的

### 原则：只包一层外壳

hifast 每个文件头都标注 `AUTOGENERATED! DO NOT EDIT! File to edit: nbs/*.ipynb`，
安装包不含 notebook，直接改源码会被升级/重装覆盖，并与上游 notebook 分叉。
所以本项目选择**外挂为主、最小补丁为辅**：

```
user → hifast（新命令）→ hifastx 各层 → 调用 hifast.<stage> → 三处钩子 → 产物
                                 ↓
                       manifest / QC 报告 / 诊断图
```

只通过**三个钩子**接触 hifast 内部，其余全部在外层完成：

| 钩子 | 位置 | 作用 |
|---|---|---|
| 产物写入 | `utils.io` 保存路径外层 | 临时文件 + 校验 + 原子 rename，避免半成品 |
| 进度 | tqdm / 保存阶段 | 把局部进度转换为结构化事件 |
| 质检 | 阶段结束、文件关闭之后 | 对该输出文件跑 QC，写侧车报告 |

钩子失效（上游升级改内部 API）时自动降级为"仅报告"，不阻断处理。

### 六个机制

| 层 | 解决什么 | 关键做法 | 用户看到什么 |
|---|---|---|---|
| 入口 | 记不住模块名与参数 | 统一子命令（`run/status/qc/plot/explain/shell/config`）+ 别名；无参数进入轻量控制台；非 TTY 退化为普通 CLI | `hifast --help` 能看懂先跑哪个 |
| 参数 | 参数能解析但不理解 | 参数元数据单一真源 → 派生 argparse 定义、help、校验、文档；语义校验；四要素错误信息；`explain`；`dry-run`；preset | 启动 5 秒内报错并给出修正示例 |
| 状态 | 进度不可知、状态不一致 | manifest 单一事实来源 + JSON Lines 进度事件 + `status` 矩阵 + 原子写 + 完成标记 + 外部链接检查 | 单行摘要 + 一屏矩阵；中断后不会误跳过 |
| 质检 | 没有自动检查 | 分阶段判据 + 三级严重度 + 三级阈值 + 批级横向对比 + 输入输出对比 + 性能预算 | 每文件一份 JSON/HTML 报告，异常标红并给处置建议 |
| 可视化 | 调参与标注依赖外部工具 | 驻波诊断套件；本地网页 RFI 标注器（兼容 `.reg` 导出）；通用 quicklook；无浏览器静态回退 | 一条命令出图；标注全程不开 CARTA |
| 编排 | 批处理靠手写 bash | 束列表、并发、内存预算、跳过已完成、链式依赖、交接报告 | 一条命令跑 19 束；`report --handover` 一页说清下一步 |

### 参数层：元数据单一真源

每个参数一条元数据：类型、单位、取值范围、默认值、物理含义、依赖关系、生效条件。
一份配置同时生成 `--help` 文案、`explain` 说明、校验规则和参数手册，
**改一处四处同步**，避免文档与行为漂移。

语义校验在启动前完成，覆盖区间反序、越界、噪声窗口压到信号、互斥参数、
依赖缺失（如选了某方法却填了另一方法的参数）、路径不可读写、数值非法、
多值参数个数不符、布尔写法过严等常见误配。

错误信息固定四要素：

```
✗ --rms_frange 1420 1423   区间反序（start > stop）
  期望  start < stop，例如 1400 1420
  原因  该区间会被当作无信号窗口估计 RMS；1423–1445 是观测频段上界
```

`--dry-run` 不读大数据，只打印解析后的完整命令、输入输出路径、预估耗时与内存、
将执行的 QC 项清单。

### 状态层：manifest + 事件流 + 原子写

- **manifest** 记录 run / stage / file / beam / 参数 hash / 起止时间 / 状态 / QC 摘要，
  作为"做到哪一步"的唯一事实来源，取代"看文件名后缀"。
- **进度事件**用 JSON Lines 流式写出（`run, stage, file, beam, step, total,
  elapsed, eta, rss`），既能渲染成不刷屏的单行摘要，也能被其他脚本消费。
- **原子写**：写 `<out>.tmp` → 回读校验 → `fsync` → `rename`；配合完成标记，
  进程被 `kill -9` 或 OOM 后不会留下"看起来完成"的文件。
  （现状是 `_check_fout()` 只做 `os.path.exists`，存在即 `sys.exit(0)`，
  让调用方误以为成功。）
- **外部链接检查**：阶段产物可能通过 ExternalLink 引用上游文件，
  移动或清理目录前先给出受影响的文件清单。

### 质检层：分阶段判据，而不是一套阈值走天下

每个阶段的物理量与故障模式不同，判据按阶段定制；跨阶段共用的只有格式/完整性项。
每个阶段四类检查：

| 类别 | 例子 |
|---|---|
| 格式与完整性 | 可打开、关键数据集存在、形状与输入一致、频率轴单调、时间轴无离群、外部链接可解析 |
| 数值分布 | NaN 比例、电平与 RMS 相对同批中位数的偏离、稳定性、整条谱线 NaN |
| 标记统计 | `is_rfi` / `is_excluded` 比例与增量、整通道被标记数、连续被标记时间长度、掩膜继承（输出 ⊇ 输入） |
| 物理量一致 | 驻波压制率与信号保留、噪声变化、参考系位移、速度轴、成图刻度闭合 |

三级阈值，越往下越依赖数据集本身：

```
L1 绝对阈值   与物理/格式常识绑定，任何数据集都不应违反，不可关闭
L2 相对阈值   与输入文件或同批其他束比较（比值、增量、相关性）
L3 基线阈值   与该数据集首次运行建立的基线比较（偏离 > k×MAD）
```

每条结论输出 `info / warn / fail` 三级严重度，并附指标、实测值、阈值、
含义与建议动作——报告要能直接指导处置，而不是只给一个红点。批级再有跨束
中位数/MAD 离群、阶段一致性、缺文件、文件大小异常。

**两个硬性工程约束**：

1. **不能把数据再读一遍**。单文件 GB 量级、单步峰值内存数十 GB，
   QC 与可视化必须采样、分块或复用处理过程中的中间量；单文件 QC 预算 ≤ 5 s
   或 ≤ 处理时间的 2%，额外内存 ≤ 500 MB。
2. **先校验数据布局**。旧的手工 QA 脚本只适用于特定形状、特定频率方向、
   特定单位的文件，且固定步长抽样会让"整通道被标记"的统计产生偏差。
   新引擎先做布局校验（维度、偏振轴位置、频率方向、掩膜维度、单位），
   整通道统计用分块整轴扫描，噪声同时报告"时间散布"与"谱线内噪声"。

### 可视化层：可复现的套件，不是截图

- **驻波诊断**：一条命令产出压制前后时间谱、FFT 幅度谱（标注 1.07 / 0.54 MHz）、
  压制率、信号保留率、参数对比图，外加一份汇总 JSON；19 束汇总图逐束给压制率与保留率。
- **RFI 标注器**：本地网页（仅监听 `127.0.0.1`，随机端口 + token，远程走 SSH 端口转发），
  载入 → 瀑布图缩放 → 框选/画线 → 掩膜预览（显示受影响的时间/频率范围与数据比例）→
  导出兼容 `.reg` 与原生 JSON → 应用。**全程不启动 CARTA。**
- **语义防错**：画"线"时显式提示"该频率全时间掩膜"，这是区域文件里最容易踩的坑。
- **回退**：无浏览器环境至少能生成静态 PNG/HTML 诊断页。

### 一次处理长什么样

```bash
hifast init --project mydata --data ~/data/beams
hifast explain sw --mw_frange        # 这个参数是什么、怎么取值、影响什么
hifast run bld --preset hi-galaxy -c 15 --dry-run
hifast run bld --preset hi-galaxy -c 15
hifast status                        # 束 × 阶段矩阵
hifast qc --last                     # 终端三行摘要 + 打开 HTML
hifast plot sw --all                 # 19 束压制率/保留率汇总
hifast report --handover             # 做到哪 / 缺什么 / 下一步命令
```

旧入口同时保留，二者等价：

```bash
python -m hifast.bld data.hdf5 -c 15 --frange 1385 1445    # 旧
hifast run bld data.hdf5 -c 15 --frange 1385 1445          # 新
```

### 判据的科学正确性怎么保证

QC 不是纯软件问题：指标是否物理上成立、阈值是否合理，需要领域评审。所以判据
不闭门拍板，按五步走：

| 步骤 | 产出 | 完成标志 |
|---|---|---|
| 1. 拟方法 | 评审稿：每阶段的物理意义、指标、算法、建议阈值 | 评审稿发出 |
| 2. 领域评审 | 对"可能出什么错、该怎么查"给意见，改阈值 | 有书面回复或批注 |
| 3. 修订 | 判据更新，每条检查有物理依据与阈值来源 | 阈值来源可追溯 |
| 4. 回放标定 | 用历史数据跑一遍，统计误报/漏报 | 已知问题类型全检出、正常数据 `fail` = 0 |
| 5. 冻结 | 判据配置 v1.0 + 阈值表 | 进入实现 |

分工原则：我们负责**可计算、可复现、可自动化**（指标怎么算、数据从哪读、报告怎么出）；
评审方负责**物理上是否成立、阈值是否合理**。评审稿只问方法，每个问题给选项和默认答案。

## 目标

| 编号 | 分目标 | 判据 |
|---|---|---|
| G1 | 质量检查内建化 | 每个阶段、每个输出文件处理完即自动出结构化 QC 报告，无需手写脚本 |
| G2 | 参数可理解、可校验 | 常见误配在启动前被拦住，并说明"错在哪、该填什么" |
| G3 | 过程可观测 | 随时能回答：第几束、第几步、还剩多久、占多少内存 |
| G4 | 诊断可视化内建 | 驻波调参与 RFI 标注不再依赖 CARTA 或临时脚本 |
| G5 | 流程可交接 | 一条链跑到哪、缺什么、下一步敲什么，由机器生成 |
| G6 | 入口直观可发现 | 打开工具就知道能做什么、下一步做什么，不必先读文档 |

**北极星指标**：一次完整批处理中，人工干预次数（手工跑脚本、手工看图、
手工改参数重跑）降到 **≤ 3 次**，且每次干预都有工具给出的明确理由。

**护栏**：QC 附加耗时 > 5%、正常数据出现 `fail` 级误报、任一旧命令输出与改进前不一致、
人工干预次数反弹——任一条成立即视为改进失败或需回退。

## 范围

| 范围内 | 范围外 |
|---|---|
| 命令行入口、子命令、别名、帮助、退出码、轻量控制台 | 基线拟合 / 驻波扣除 / RFI 检测 / 成图算法 |
| 参数元数据、语义校验、`explain`、`dry-run`、预设 | 任何默认参数值 |
| 进度事件、单行摘要、`status`、run 目录与日志规范 | HDF5 内部结构（数据集/组） |
| 分阶段 QC 指标与判据、JSON/HTML 报告、批级一致性 | 桌面 GUI 或 Web 服务平台 |
| 驻波诊断、RFI 标注、通用 quicklook | 替代 CARTA 的全部功能 |
| 批处理编排、manifest、原子写、半成品检测 | Windows 支持、GPU / 分布式调度 |

**五条硬约束**

1. **科学结果不变**：相同输入 + 相同参数 → 相同输出（允许新增 header attrs）。
2. **旧命令仍可用**：`python -m hifast.<stage> ...` 行为不变。
3. **默认不阻断**：QC 默认只报告，退出码语义不变；阻断需显式开启（`--qc strict`）。
4. **数据格式不变**：只允许新增属性，不新增/改名数据集。
5. **不引入重依赖**：服务器常离线，新增代码优先标准库 + hifast 已有依赖。

## 里程碑

| 里程碑 | 目标 | 退出标准 |
|---|---|---|
| **M0** 规格冻结 | 目标、范围、判据草案达成一致 | 决策项全部有结论；判据有领域评审反馈 |

| **M2** 参数层 | 可查、可校验、可预演、入口直观 | 常见误配 100% 启动前拦截 |
| **M3** 状态与进度 | 过程可见、断点安全 | `status` 可用；`kill -9` 后不误把半成品当成品 |
| **M4** 可视化 | 驻波与 RFI 不再依赖外部工具 | 一条命令出诊断套件；标注全程不开 CARTA |
| **M5** 整合与交接 | 一条链跑通、可交接 | 旧命令输出逐值一致；新用户 15 分钟跑通一个阶段 |

推进顺序 **M1 → M2/M3 并行 → M4 → M5**：QC 是用户感知最强、也最能验证判据是否
合理的一环；参数层与状态层是基础设施，越早稳定越省返工。
